## Functional evidence

- Before overlay, `water` VI page 1 had only one result and page 2 was empty; frontend VI Live Search returned 502. After overlay, CMS `water&lang=vi&per=3` reports total **101**, 34 pages; pages 1 and 2 have distinct IDs and VI language. EN reports total **37**, 13 pages, with EN language. Core `/wp/v2/posts?search=water` total 138 equals 101+37 in this sample; this supports no loss of overall matching count for this term, not ranking equivalence. Accented `thủy lợi` VI yielded 6818 results; `Kyoto` VI 25 and EN 2. The new language-scoped path uses WordPress `WP_Query` ranking rather than WPX FULLTEXT ranking, so result order can change. Unscoped/direct WPX search is a separate path.
- An out-of-range WordPress query originally returned `total=0`; a regression test reproduced it. SearchService now asks page 1 for totals only when the requested page is empty beyond page 1. Live `water` VI page 35 returns `items=[]`, `total=101`, `total_pages=34`, `page=35`; EN page 14 returns its 37/13 totals. Repeated VI/EN search returned separate stable totals, correct locale URLs and `Cache-Control: public, max-age=0, s-maxage=30, stale-while-revalidate=60`.
- CMS SEO for existing post ID `56168` returned 200. Invalid ID `999999999` returned an Nginx HTML 404 rather than the intended JSON error; investigate separately. CMS PHP-FPM was active with `NRestarts=0`, no recent error-priority journal entries in the preflight window; load was about 5.8/6.2/6.2 on 16 CPUs, RAM roughly 11/23 GiB, swap 2.0/3.8 GiB. These are point-in-time health checks.
- Frontend adapter calls `/headless/v1/search` once with `q`, `lang`, `page`, `per_page`, and rejects malformed, mixed-language or invalid URL responses instead of reporting an empty success. Local targeted parser tests (4), PHP Search/SEO contract tests, PHP lint, TypeScript, ESLint and frontend build passed. Isolated VPS `npm ci` and build passed. On live staging, targeted Playwright tests passed **3/3**: VI and EN Live Search → Enter → results → article → pagination, plus EN locale isolation. Frontend public API and Search Pages for both languages returned 200 with release header `828581d`.

## Performance and remaining blockers

- A staging homepage request timed out after **20 s** despite other routes returning 200; a subsequent VI homepage request took **9.68 s**. Direct CMS `/headless/v1/homepage?lang=vi` took **7.92 s** in a nearby sequential sample, showing a substantial upstream contribution. Earlier CMS homepage samples were 6.71 s VI / 7.32 s EN. This locates the slow path at least partly in CMS snapshot generation but does not establish whether SQL, PHP serialization, internal REST calls or cache misses dominate. The installed 2.1.0 `HomepageSnapshotService` is not present in the local 2.0.9 source, so no unverified optimization was deployed.
- After warm cache, three sequential VI homepage requests took **0.468/0.432/0.437 s**, EN **0.366/0.420/0.409 s**; VI Search Page 1 **0.298/0.255/0.294 s**, page 2 **2.487/0.284/0.239 s**. The cold/uncached failures still violate the agreed cold document ≤5 s gate, even though warmed responses can be fast. These small, cache-dependent samples are not a defensible p95. Search VI page 2 also took 12.52 s in an earlier staging smoke pass; a CMS `Kyoto` VI search took 8.19 s.
- The baseline before this deployment had one `/en` HTTP 200 that delivered only 162 KB then timed out at 18 s. The current limited smoke and targeted E2E did not reproduce that precise partial response; no server-level root cause has been proven. `journalctl -u tlu-next-staging -p warning` showed one exit-code event during the deliberate release switching, while the current service is active with `NRestarts=0`. Preserve response-size/timeout checks in the next longer sampling run.
- `cms.nguyenhongson.vn` did not resolve during preflight; tests targeted `cms.tlu.edu.vn` directly. Existing WPX FULLTEXT local source/test edits remain uncommitted and were not deployed by this overlay. The prior divided-score WPX candidate failed live MariaDB validation; do not present it as a production fix.

**Next gate:** profile phases of the installed 2.1.0 homepage snapshot on the CMS and correlate slow requests with PHP-FPM/Nginx timings; resolve the invalid-ID SEO response and investigate the prior partial `/en` transfer. Repeat bounded cold and warm navigation/search samples on this exact release, checking complete bytes and content, then compare with the agreed warm p95 ≤2 s and cold document p95 ≤5 s.
