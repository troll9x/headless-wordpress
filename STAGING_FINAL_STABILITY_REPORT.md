## Performance and release gate

Baseline samples in `artifacts/staging-debug/before-http.json` measured HTML TTFB about 5.1–16.6 s and frontend loopback `/en` 6.2 s; these are observed samples, not a controlled cold/warm p95. No valid after benchmark can be reported because CMS saturation made the new release and even the old release time out. The agreed gates remain warm navigation/search p95 ≤2 s, cold document p95 ≤5 s, and complete content. They are **not met or not measurable** in the current state.

CMS administration should first identify the heavy PHP-FPM work and access/query source using access/error logs, PHP-FPM status/slowlog and database process information. This report does not authorize restarts, database edits or production changes. Once `/wp/v2/search` and homepage APIs respond reliably and load normalizes, build a new isolated worktree at the final branch SHA, run staging E2E and Chrome acceptance, measure before/after p50/p95 and Web Vitals, and verify content across homepage/category/article routes. A CMS search endpoint with actual Polylang filtering is needed for exact language-specific totals and dense pagination. Do not proceed with Go Production until those checks and separate data, backup/restore and cutover gates pass.
