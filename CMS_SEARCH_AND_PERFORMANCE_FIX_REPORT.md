Live comparison against intended CMS results, especially accented/unaccented queries, is a deployment gate; the local mocks cannot establish relevance or prove that all expected posts are found.
- Targeted local test `php scripts/test-cms-language-search.php` passed for mixed VI/EN fixtures, total/pages, last page, password exclusion, page exclusion, `per_page`, invalid language and fail-closed mismatches. ## WPX FULLTEXT ranking investigation — 2026-10-13

**Local code fix prepared; CMS remains unfixed/unverified.** The failing SQL comes from active WPCode PHP snippet `50120` (“WP Fulltext Search”), `WPX_FT_LocalIndex::rest_search()`, `ORDER BY` expression `phr_score*10`. `phr_score` is `MATCH(idx.title,idx.content,idx.slug,idx.keywords,idx.plain) AGAINST ('"<query>"' IN BOOLEAN MODE)` over the InnoDB `wpx_ft_index` row built from post title, slug, taxonomy names, trimmed body, and an unaccented text copy. The error occurs when multiplying a sufficiently large finite DOUBLE relevance value by 10; a row value greater than `DBL_MAX/10` would suffice. The log does not disclose the actual score or explain why MariaDB produced it. The WHERE FULLTEXT filter itself was not shown to fail.

The local WPCode source copy at `release/wpx-fulltext/wpcode-snippet-50120.php` now scales every component of the same weighted sum by 1/64 **before** weighted multiplication or addition. The title-hit and prefix priority and date tie-break are unchanged. For finite relevance values, the new score is the old score divided by 64, so the intended order is preserved subject to normal floating-point rounding; the sum of FULLTEXT coefficients is only 17/64. No score is clamped or silently replaced. The snippet was exported read-only; it has **not** been edited in WPCode on CMS. The Headless API three-file VI/EN overlay is also unchanged and undeployed. Once deployed, its `lang=vi|en` `WP_Query` search would bypass this WPX expression, while unscoped search and direct WPX search would remain affected until the snippet fix is deployed. `/suggest` uses WPX matching but a date-only sort.

The targeted regression test first failed against the original snippet and passed after the patch. It demonstrates overflow at `2e307 * 10`, checks finite output at the DOUBLE boundary, and compares ordinary VI/EN/water ranking weights and large-score order. PHP lint passed. These are local source/arithmetic tests, not a MariaDB FULLTEXT execution. No isolated MariaDB service was available (Docker daemon not running), and CMS REST instability prevents safe live ranking validation. Next read-only diagnostic on a healthy CMS: select raw `phr_score`, `phr_plain_score`, `ft_score` for a few `water` matches without multiplying them, then compare VI/EN term recall and order. Recheck and back up WPCode snippet 50120 separately before any edit; retain the exact export for rollback. Do not mark search FIXED until both CMS routes and staging search pass.
